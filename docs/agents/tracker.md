# Конфигурация трекера для агентов

Трекер проекта — GitHub Issues репозитория `TiltStable/frontend-project-387`.
Работа агента с трекером ведётся через `gh` CLI. Секретов в конфигурации нет:
авторизация — через окружение агента (`gh auth`).

## Исходный проект

Приложение перенесено из репозитория
[`TiltStable/frontend-project-386`](https://github.com/TiltStable/frontend-project-386)
(«Календарь звонков»). Оригинальные документы процесса живут в issues того
репозитория, ссылки сохранены:

- [Карта решений — issue #1 в 386](https://github.com/TiltStable/frontend-project-386/issues/1):
  все принятые решения с ответами и обоснованиями.
- [Спецификация — issue #2 в 386](https://github.com/TiltStable/frontend-project-386/issues/2):
  зеркало каноничного файла [docs/spec.md](../spec.md).
- Тикеты реализации #3–#8 в 386 — история исходной реализации
  (вертикальные срезы, закрытие коммитами с sha, мутационная проверка
  в #5 в 386).

Ссылки вида «#N» без пометки в этом документе относятся к трекеру текущего
репозитория (387); ссылки на исходный проект всегда помечены «в 386».

## Точка входа агента

Перед началом работы прочитать в этом порядке:

1. Карта решений (issue #1 в 386, ссылка выше): все принятые решения
   с ответами и обоснованиями.
2. Спецификация (issue #2 в 386) и каноничный файл
   [docs/spec.md](../spec.md): роли, пользовательские истории
   (US-1..US-5), правила окна и занятости, контракты API, границы
   тестирования.
3. [GLOSSARY.md](../../GLOSSARY.md) — словарь терминов, единые формулировки.
4. Открытые тикеты текущего репозитория: `gh issue list --state open`.

## Конвенции тикетов

- Тикет реализации: цель, чеклист шагов (контракт → генерация → сервер →
  интерфейс → тесты), раздел «Зависимости» с номерами issues, ссылка на
  спецификацию ([docs/spec.md](../spec.md)).
- Один тикет — одна вертикальная функция, проходящая все слои.
- Зависимости указываются явно («требует #N»); работа не начинается раньше
  закрытия зависимостей.
- Реализованный тикет закрывается комментарием со ссылкой на коммит (sha),
  закрывающий чеклист.
- Reference-issues (карта решений, спецификация) не закрываются; в 386
  для этого служили #1 и #2.
- Изменение API начинается с контракта (см.
  [implement-spec.md](implement-spec.md) → «Порядок правки контракта»),
  затем тикет обновляет чеклист реализации.

## Коммиты

- Conventional Commits обязательны (`feat:`, `fix:`, `docs:`, `test:`, `ci:`).
- Коммит реализации ссылается на тикет, который закрывает:
  `feat: запись на свободный слот (#12)`.
- Commits-msg хук (hk) отклоняет сообщения вне формата.

## Пример пройденного цикла

В исходном проекте 386 тикеты #3–#8 (типы событий → слоты → бронирование →
страница владельца → e2e) прошли полный цикл: спецификация (#2 в 386) →
зависимый граф → реализация коммитами `(#N)` → закрытие с sha → мутационная
проверка правила бронирования записана в тикете #5 в 386.
