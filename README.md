# Календарь звонков

[![hexlet-check](https://github.com/TiltStable/frontend-project-387/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/TiltStable/frontend-project-387/actions)

**Демо:** <https://call-calendar-rt25.onrender.com> — бесплатный инстанс Render
засыпает после 15 минут простоя, первый запрос будит его примерно за минуту.

Сервис бронирования звонков, разработанный совместно с ИИ. Владелец календаря
публикует типы встреч и доступное для них время, а гость без регистрации
выбирает свободный слот на ближайшие 14 дней и записывается на звонок.

Референс пользовательского сценария: [Cal.com](https://cal.com).

Учебный проект Хекслета: https://ru.hexlet.io/programs/frontend
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарий

Путь повторяет Cal.com в упрощённом виде: владелец задаёт расписание и
создаёт типы встреч (в Cal.com это Availability и Event Types), делится
ссылкой, гость открывает страницу бронирования, выбирает день и слот,
подтверждает запись, и встреча появляется в списке владельца (в Cal.com это
Bookings → Upcoming). Регистрации, внешние календари и уведомления Cal.com
в проект не входят.

### Владелец

1. Владелец календаря один и задан заранее, регистрации в приложении нет.
2. Заводит типы встреч. У каждого типа есть название, описание и длительность.
3. Смотрит список своих типов встреч.
4. Смотрит список предстоящих встреч всех типов. Новая запись гостя
   появляется в этом списке.

### Гость

1. Заходит в приложение без регистрации и видит типы встреч владельца.
2. Выбирает тип встречи и открывает календарь на ближайшие 14 дней.
3. Выбирает свободный слот и записывается на звонок. Слот длится столько,
   сколько выбранный тип встречи.
4. Запись появляется в списке предстоящих встреч владельца.

## Ограничения приложения

- Нет авторизации, личных кабинетов, уведомлений и интеграций с внешними
  календарями. Функциональность намеренно ограничена.
- Владелец календаря один и задан заранее.
- Окно записи занимает 14 календарных дней и сдвигается с течением времени.
  Начало окна: с завтрашнего дня. Часы работы владельца: 09:00–18:00 по
  будням. Часовой пояс: Europe/Moscow. Значения зафиксированы в
  [docs/spec.md](docs/spec.md).
- Длительность слота совпадает с длительностью выбранного типа события,
  шаг доступных стартов: 15 минут, общий для всех типов.
- Пересечение интервалов запрещено, включая частичное наложение встреч
  разных типов. Следующая встреча может начинаться в момент окончания
  предыдущей. Правила действуют и для двух запросов, пришедших одновременно:
  интервал занимает только одна запись.
- Хранение данных: память процесса. Перезапуск сервиса (в том числе
  перезапуск контейнера и засыпание free-инстанса Render) сбрасывает типы
  событий и брони. Интерфейс хранилища позволяет позже заменить его на базу
  данных без изменения доменной логики.

## API и генерация клиента

- Контракт API описывается на TypeSpec.
- OpenAPI-спецификация генерируется из TypeSpec-контракта.
- Для фронтенда из OpenAPI-спецификации генерируется клиентский SDK.
  До выбора инструментов проверяется, что для языка фронтенда есть
  генератор клиента из OpenAPI.
- Серверные типы и маршруты генерируются, если выбранный фреймворк это
  поддерживает. При отсутствии серверного генератора бекенд реализуется
  по контракту и проверяется тестами.

## Стек

- TypeScript, монорепо на npm workspaces (`apps/backend`, `apps/frontend`)
- Backend: Node.js + [Hono](https://hono.dev/)
- Frontend: React 19 + [Vite](https://vite.dev/) + [Mantine](https://mantine.dev/)
- Контракт: [TypeSpec](https://typespec.io/) → OpenAPI → клиентский SDK
  ([@hey-api/openapi-ts](https://heyapi.dev/))
- Тесты: Vitest; линт и формат: oxlint + oxfmt
- Окружение: [mise](https://mise.jdx.dev/) (версии в `mise.toml`), git-хуки
  через [hk](https://hk.jdx.dev/); CI: GitHub Actions (`mise run check` на
  каждый push)

## Установка

Нужен Node >= 22.18, рекомендуется установка инструментов через [mise](https://mise.jdx.dev/).

```bash
git clone https://github.com/TiltStable/frontend-project-387.git
cd frontend-project-387
mise install   # ставит node, hk, pitchfork по mise.toml
npm install
hk install     # git-хуки: pre-commit (lint + format), commit-msg (Conventional Commits)
```

## Использование

```bash
mise daemons start        # backend :3000 + frontend :5173 в фоне
mise daemons stop        # остановить
mise daemons status      # состояние
```

Без mise те же серверы по отдельности: `npm run dev:backend`,
`npm run dev:frontend`.

Если порт 3000 или 5173 занят другим процессом, `mise daemons start` может
сообщить о готовности, а приложение упадёт уже внутри: смотрите логи,
`mise daemons logs backend` / `mise daemons logs frontend`.

- API: http://localhost:3000/health
- UI: http://localhost:5173

Все проверки (линтер, формат, типы, тесты, сборка) одной командой:

```bash
mise run check   # или npm run check без mise
```

`mise run check` — полный набор: он дополнительно повторяет генерацию
контракта и SDK с проверкой отсутствия изменений (`npm run gen:check`) и
запускает браузерный e2e-сценарий (Playwright против настоящих backend
и frontend, без подмены ответов):

```bash
npx playwright install chromium   # один раз, браузер для e2e
npm run e2e
```

## Docker и деплой

Приложение упаковано в один контейнер: он слушает порт из переменной
окружения `PORT` и отдаёт и API, и собранный фронтенд.

```bash
docker build -t call-calendar .
docker run --rm -p 4000:4000 -e PORT=4000 call-calendar
# http://localhost:4000 — SPA и API на одном порту
```

Прод-режим локально без Docker — `node apps/backend/dist/index.js` из корня
репозитория после `npm run build` (путь к статике относительный).

Деплой — [Render](https://render.com), Blueprint в `render.yaml`: web-сервис
собирается из Dockerfile ветки `main` и автодеплоится на каждый коммит.
Демо-адрес выше обслуживается инстансом, подключённым к исходному репозиторию
[frontend-project-386](https://github.com/TiltStable/frontend-project-386);
к этому репозиторию Render-сервис пока не подключён, поэтому Blueprint из
`render.yaml` создаст отдельный сервис со своим URL. Free-инстанс засыпает
после 15 минут простоя (см. «Демо» выше).

### MCP-сервер Render

В репозитории есть проектная конфигурация `.mcp.json`: Render MCP подключается
по адресу `https://mcp.render.com/mcp`, токен читается из переменной
окружения `${RENDER_API_KEY}` — секретов в репозитории нет.

Два способа авторизации:

- **API-ключ** (без браузера): Account Settings → API Keys → Create API Key,
  затем положить его в переменную окружения, например
  `setx RENDER_API_KEY "<ключ>"`, либо в корневой `.env` (файл заигнорен).
  Переменную читают и `.mcp.json`, и автоматизация деплоя.
- **OAuth** (в редакторе с поддержкой MCP): при первом обращении к серверу
  Render откроется браузерная авторизация; токены сессии хранятся локально
  у агента и в git не попадают.
